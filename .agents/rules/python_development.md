# Python 多模块项目开发规范

本规范适用于由开发者与 AI 助手共同维护的中大型 Python 项目。目标是让代码在持续演进、多人协作和自动化生成场景下，仍具备清晰边界、可靠测试、可追溯变更与稳定交付能力。

文中的“必须”是强制要求，“应”是默认要求，“可”是按需选择。确需偏离强制要求时，必须在 ADR（Architecture Decision Record）或变更说明中记录原因、影响和替代保障。

---

## 1. 核心原则

1. **正确性优先**：先保证行为、数据一致性和安全，再考虑抽象复用与性能优化。
2. **模块边界优先**：按业务能力划分模块，禁止以全局 `services/`、`models/`、`utils/` 承载全部业务。
3. **显式契约**：跨模块、跨进程和外部接口必须具有明确、可验证、可版本化的契约。
4. **依赖方向稳定**：核心业务规则不得直接依赖 Web 框架、消息中间件或第三方 SDK。
5. **小步可验证**：每次变更应聚焦单一目标，并通过测试、静态检查和审查。
6. **可观测与可恢复**：关键流程必须可定位、可重试、可审计，并明确失败策略。
7. **AI 输出不享有默认信任**：AI 生成代码必须经过与人工代码相同的检查、测试和评审。
8. **避免过度设计**：无明确需求时采用模块化单体；只有在组织、部署或扩缩容边界明确后才拆分微服务。

## 2. 标准技术栈

### 2.1 基础工具链

- **Python**：使用 `Python 3.12+`；若受部署环境限制，可降至 `3.11+`，并在 `pyproject.toml` 中明确。
- **项目与依赖管理**：默认使用 `uv` 和 `pyproject.toml`，提交 `uv.lock` 以保证可复现安装。
- **构建后端**：默认使用 `hatchling`；若仓库已有成熟方案，可继续使用。
- **代码检查与格式化**：使用 `Ruff`。
- **静态类型检查**：使用 `Pyright`，新代码采用严格模式。
- **测试框架**：使用 `pytest`、`pytest-cov`；异步测试使用 `pytest-asyncio`。
- **Git 钩子**：可使用 `pre-commit`，但 CI 才是最终质量门禁。

禁止使用 `pip freeze > requirements.txt` 作为项目依赖管理方案。它无法区分直接依赖与传递依赖，也不适合作为跨平台、可维护的依赖声明。

### 2.2 应用技术栈

- **HTTP API**：默认使用 `FastAPI`，运行时使用 `Uvicorn`。
- **数据契约与配置**：使用 `Pydantic v2` 与 `pydantic-settings`。
- **HTTP 客户端**：使用 `httpx`，集中配置超时、连接池、重试和追踪。
- **关系数据库**：需要关系数据库时，默认使用 `SQLAlchemy 2.x` 与 `Alembic`。
- **日志**：使用标准库 `logging` 的结构化配置，生产环境输出 JSON。
- **遥测**：需要跨服务诊断时使用 OpenTelemetry 接入日志、指标和链路追踪。

任务队列、缓存、搜索引擎、工作流引擎等基础设施不得仅因“未来可能需要”而引入。引入前必须明确使用场景、失败语义、运维成本与退出方案。

### 2.3 框架使用边界

FastAPI、Pydantic 和 SQLAlchemy 用于解决特定技术问题，不应主导业务模块设计：

- 核心业务规则不得导入 `fastapi`、HTTP 客户端或厂商 SDK。
- Pydantic 模型用于系统边界的数据解析与序列化，不应取代复杂业务中的行为模型。
- ORM 模型不得直接作为 API 响应或跨模块契约。以数据增删改查为主的简单模块可在模块内部直接使用 ORM 模型，无需机械复制一套领域实体。
- 框架替换不应迫使核心业务规则重写。

## 3. 项目与模块结构

### 3.1 组织策略

大型 Python 应用普遍采用“业务模块优先、模块内按职责组织”的结构。默认使用 `src` 布局，业务包直接以 `orders`、`accounts`、`billing` 等领域名称命名，不强制增加 `modules/` 中间层，也不要求每个模块机械创建相同的四层目录。

```text
<project_root>/
├── .agents/rules/                 # AI 与工程规则
├── docs/
│   ├── architecture.md            # 总体架构和依赖关系
│   └── adr/                       # 架构决策记录
├── src/<project_name>/
│   ├── app.py                     # 应用工厂、生命周期和路由装配
│   ├── core/                      # 配置、日志、安全等项目级能力
│   ├── api/                       # 全局路由聚合、中间件和异常映射
│   ├── accounts/                  # 账户业务模块
│   │   ├── api.py                 # HTTP 入口；复杂时可拆为 api/
│   │   ├── models.py              # ORM 模型或模块内部数据模型
│   │   ├── schemas.py             # 输入输出契约
│   │   ├── services.py            # 业务用例与流程编排
│   │   ├── repositories.py        # 持久化访问；按需创建
│   │   ├── permissions.py         # 授权规则；按需创建
│   │   ├── tasks.py               # 后台任务入口；按需创建
│   │   ├── events.py              # 领域/集成事件；按需创建
│   │   └── exceptions.py          # 模块错误
│   ├── orders/                    # 订单业务模块
│   │   └── ...
│   ├── integrations/              # 跨模块共享的外部系统客户端
│   └── shared/                    # 少量稳定、无业务归属的公共能力
├── tests/
│   ├── unit/                      # 无外部资源的快速测试
│   ├── integration/               # 数据库、缓存、消息等集成测试
│   ├── contract/                  # 模块或外部接口契约测试
│   └── e2e/                       # 少量关键链路测试
├── migrations/                    # 数据库迁移
├── scripts/                       # 可重复执行的运维和开发脚本
├── pyproject.toml                 # 项目、工具和依赖的唯一主配置
├── uv.lock                        # 锁定依赖
└── README.md
```

模块初期应优先使用语义明确的单文件，如 `services.py`、`schemas.py`。当文件职责增多或规模明显增长时，再拆为同名子包，例如 `services/`、`schemas/`。禁止为了符合模板而创建空目录、只有一个实现的抽象层或无业务价值的 DTO 转换。

### 3.2 常用职责命名

- **api**：HTTP 路由、请求解析、认证上下文和响应映射，不承载业务规则。
- **schemas**：Pydantic 输入输出模型以及公开数据契约。
- **models**：ORM 模型或模块内部数据模型，不直接充当外部契约。
- **services**：业务用例、流程编排和事务边界。名称过于宽泛时，应按用例拆分为 `create_order.py` 等具体模块。
- **repositories**：封装复杂查询和持久化访问；简单查询无需为了分层而强制增加仓储。
- **clients/integrations**：第三方 API、消息、缓存和文件系统适配。
- **tasks/consumers**：后台任务和消息消费入口，只负责解析消息并调用业务服务。
- **events**：模块内部事件和跨模块集成事件。
- **core**：仅放项目级配置、日志、安全、生命周期等基础能力，不得成为业务代码收容目录。
- **shared**：仅放语义稳定且确实跨模块复用的代码。

推荐的主要调用方向：

```text
api / cli / tasks / consumers
              │
              ▼
     services / use_cases
          │           │
          ▼           ▼
 models / rules   repositories / clients
```

入口层不得直接实现业务流程或跨越服务层操作多个资源。业务模块之间不得读取对方的私有表、导入内部实现或绕过公开服务。

### 3.3 何时采用完整分层

当模块具有复杂且长期稳定的业务规则、多种入口或基础设施实现，或需要脱离框架进行独立测试时，可在该模块内部采用 Clean Architecture/DDD 命名：

```text
orders/
├── domain/                         # 实体、值对象、领域规则和事件
├── application/                    # 用例、事务编排和端口
├── infrastructure/                 # ORM、仓储和外部服务实现
└── presentation/                   # HTTP、CLI、任务和消息入口
```

这是一种按复杂度启用的可选结构，不是所有模块的默认模板。只提供 HTTP 的模块可使用更直观的 `api/` 代替 `presentation/`；只有一个持久化实现时，也不应无条件增加接口和实现两套文件。

### 3.4 跨模块协作

- 同进程同步调用应通过目标模块公开的服务、用例或 Facade。
- 解耦或异步流程应使用带版本的集成事件。
- 跨模块 DTO 必须稳定、最小化，并与模块内部 ORM/Pydantic 模型分离。
- 公共代码只有在语义稳定且至少被两个模块实际复用时才可进入 `shared/`。
- 禁止创建无边界的 `common.py`、`helpers.py` 或 `utils.py`；工具应按职责命名。
- 模块循环依赖必须通过重新划分职责、事件或端口消除，不得用延迟导入掩盖。

## 4. 依赖与配置管理

### 4.1 依赖规则

- 运行、开发和可选依赖必须在 `pyproject.toml` 中分组声明。
- 必须提交锁文件；CI 使用锁文件进行冻结安装。
- 新增依赖前必须检查维护状态、许可证、安全记录、包体积和现有能力是否已能满足需求。
- 禁止从未固定分支、个人临时仓库或不可信 URL 安装生产依赖。
- 依赖升级应独立成批，执行测试并记录可能的破坏性变更。
- CI 应执行依赖漏洞扫描；高危漏洞必须阻断发布或形成有期限的风险豁免。

### 4.2 配置规则

- 配置只从环境变量、受控配置文件或密钥管理系统读取。
- 使用 `pydantic-settings` 在启动阶段完成类型校验；关键配置缺失时快速失败。
- 本地可提供 `.env.example`，不得提交真实 `.env`、令牌、私钥或生产连接串。
- 配置对象应通过依赖注入传递，禁止在业务模块中散落读取环境变量。
- 开发、测试、预发布和生产环境使用同一套配置结构，不通过代码分支改变业务行为。

## 5. 编码与类型规范

### 5.1 风格与命名

- 遵循 PEP 8、PEP 257 和项目 Ruff 配置。
- 包、模块、函数和变量使用 `snake_case`；类使用 `PascalCase`；常量使用 `UPPER_SNAKE_CASE`。
- 名称必须表达业务含义，避免 `data`、`info`、`manager`、`handler` 等过度宽泛的命名。
- 函数应保持单一职责；出现多层嵌套时优先使用提前返回或拆分用例。
- 注释解释“为何如此”和约束背景，不复述代码。
- 项目文档、注释和 Docstring 默认使用简体中文；公开 API 中已有的英文术语和协议字段保持原名。

### 5.2 类型要求

- 所有公开函数、方法、类属性和模块边界必须具有完整类型。
- 新代码必须通过 Pyright 严格检查；不得批量添加 `# type: ignore`。
- 必须忽略类型错误时，使用最窄的错误码并附原因，例如 `# type: ignore[reportUnknownMemberType]`。
- 优先使用 `Protocol` 描述行为接口，使用 `dataclass` 表达内部数据对象，使用 Pydantic 表达边界数据。
- 禁止无理由使用 `Any`、裸 `dict`、裸 `list`；动态外部数据应先作为 `object` 接收，再显式校验。
- 金额使用 `Decimal` 或明确的最小货币单位整数，不得使用 `float`。
- 时间使用带时区的 `datetime`，系统内部统一为 UTC，边界处再进行时区转换。
- 标识符类型必须一致；需要防止混用时使用 `NewType` 或值对象。

### 5.3 函数与错误

- 公共函数必须使用 Google 风格 Docstring；简单、语义显然的私有函数可省略。
- 禁止使用可变对象作为默认参数。
- 禁止空泛捕获 `except Exception` 后静默继续；边界层统一兜底记录后可转换为稳定错误。
- 领域错误使用明确的异常类型或结果类型表达，不使用字符串匹配判断错误。
- 异常消息不得包含令牌、密码、完整 SQL、个人敏感数据或内部堆栈。
- 资源必须通过上下文管理器或生命周期钩子释放。

## 6. 并发与异步规范

- 只有存在真实异步 I/O 链路时才使用 `async def`，不得为了形式统一把纯同步代码改为异步。
- 异步调用链中禁止直接执行阻塞 I/O；应使用异步驱动、线程池或任务队列。
- HTTP、数据库、缓存和消息调用必须设置超时；禁止无限等待。
- 重试仅用于临时性失败，并使用有限次数、指数退避和随机抖动。
- 非幂等操作不得盲目重试；写操作应使用幂等键、唯一约束或去重机制。
- 并发共享状态必须明确同步策略；不得依赖单进程内全局变量维持业务一致性。
- CPU 密集任务应移出 Web 请求进程，交由工作进程或独立计算服务处理。
- 后台任务必须有持久化、失败处理和可观测性要求；关键任务不得只依赖 FastAPI 进程内 `BackgroundTasks`。

## 7. API 与边界契约

### 7.1 FastAPI 入口

- 使用应用工厂或明确的 bootstrap 入口创建 `FastAPI` 实例，禁止在导入模块时执行网络连接或迁移。
- 路由使用 `APIRouter` 按模块组织，并采用明确的版本策略，如 `/api/v1`。
- 路由函数保持精简：解析请求、执行认证授权、调用用例、映射响应。
- 每个端点必须声明响应模型、成功状态码和可能的稳定错误响应。
- API 不得返回 ORM 对象、内部异常、堆栈或未经筛选的第三方响应。

### 7.2 契约设计

- 请求与响应使用不同模型，创建、更新和读取模型不得为图省事而混用。
- PATCH 必须区分“未提供字段”和“显式设为空”。
- 分页、排序、过滤、日期和错误格式应在项目级统一。
- 列表接口必须设置分页和最大页大小，禁止无界查询。
- 外部可见字段、枚举和事件一旦发布即视为契约；破坏性变更必须版本化。
- 错误响应至少包含稳定的 `code`、面向调用方的 `message` 和关联请求的 `trace_id`；HTTP 状态码必须符合语义。
- OpenAPI 是 HTTP 契约的一部分；CI 应检测非预期的破坏性变更。

### 7.3 认证与授权

- 认证负责确认身份，授权负责判断是否允许执行具体动作，两者不得混为一体。
- 授权必须在服务端按资源和动作校验，不能依赖前端隐藏入口。
- 默认最小权限；敏感操作需要审计记录，必要时实施二次确认或双人审批。
- 密码只使用成熟的自适应哈希算法；令牌必须有过期、撤销和轮换策略。

## 8. 数据持久化与事务

- 复杂持久化访问应通过仓储或查询对象封装；仅在存在替换实现、稳定边界或独立测试价值时声明抽象接口。
- 一个应用用例应具有明确事务边界；提交和回滚不得散落在多个仓储方法中。
- 禁止在循环中隐式触发 N+1 查询；关键查询需检查执行计划和索引。
- 数据库约束是最终一致性保障，重要唯一性和引用完整性不得只靠应用校验。
- 所有 Schema 变更必须通过 Alembic 迁移，禁止生产环境自动 `create_all`。
- 迁移应支持滚动发布：优先采用“扩展—迁移数据—切换代码—收缩”的兼容流程。
- 破坏性迁移、大表回填和索引创建必须评估锁表时间、回滚和备份恢复。
- 涉及数据库与消息的一致性时，优先使用事务发件箱（Transactional Outbox）等可靠模式。
- 测试和日志中使用的数据必须脱敏；生产数据不得直接复制到非生产环境。

## 9. 测试策略

### 9.1 测试分层

- **单元测试**：覆盖核心业务规则和服务用例，快速、确定、无网络和真实数据库依赖。
- **集成测试**：验证 ORM 映射、迁移、仓储、缓存、消息和第三方适配器。
- **契约测试**：验证模块公开 API、OpenAPI、事件 Schema 和外部服务交互。
- **端到端测试**：只覆盖少量关键业务链路，不代替低层测试。

测试重点是行为和风险，不以追求单一覆盖率数字代替有效断言。新增或修改的核心业务代码应达到高分支覆盖；项目可在 CI 中设置总体覆盖率下限并逐步提高。

### 9.2 编写要求

- 测试文件和函数分别使用 `test_*.py`、`test_*` 命名。
- 测试遵循 Arrange-Act-Assert 或 Given-When-Then，每个测试只验证一个清晰行为。
- 测试名称必须描述场景与预期结果，例如 `test_create_order_rejects_inactive_customer`。
- 必须覆盖正常路径、边界条件、权限失败、依赖失败和幂等/重试行为。
- 修复缺陷时，必须先添加能复现缺陷的回归测试。
- 时间、随机数、UUID 和环境差异应可注入或固定，禁止依赖 `sleep` 解决竞态。
- 使用工厂或 builder 创建测试数据，避免复制庞大的字典和 fixture。
- 数据库集成测试必须隔离数据；优先使用临时真实数据库或容器，不用 SQLite 模拟与生产不同的数据库语义。

### 9.3 Mock 边界

- Mock 外部系统和不稳定边界，不 Mock 被测对象内部实现细节。
- Patch 必须作用于“被使用的位置”，并使用 `spec`/`autospec` 限制接口。
- 仓储、消息和 HTTP 适配器至少应有真实集成或契约测试，不能只有 Mock 测试。
- 禁止 Mock 掉核心业务规则后仅断言“方法被调用”。
- 快照测试只用于稳定且经过审查的输出，不得用大面积更新快照掩盖行为变化。

## 10. 日志、监控与运行可靠性

- 使用模块级 logger，禁止在生产代码中使用 `print`。
- 日志应结构化，并包含 `trace_id`、请求/任务标识、模块、事件名和结果；不得记录密钥和敏感正文。
- 预期业务拒绝使用适当级别记录，未知异常记录堆栈且只返回通用外部错误。
- 对关键入口记录延迟、吞吐量、错误率和资源饱和度。
- 外部依赖调用应记录目标、耗时、结果类别和重试次数，敏感参数必须脱敏。
- 应提供存活与就绪探针；就绪检查反映实例是否能接收流量，避免执行高成本深度检查。
- 服务必须支持优雅关闭：停止接收新任务、完成或转移在途任务、释放连接。
- 告警必须对应可执行处置，核心故障应有 Runbook。

## 11. 安全规范

- 所有外部输入均不可信，必须在系统边界进行类型、长度、格式和业务权限校验。
- 数据库操作必须参数化；禁止拼接 SQL。
- 文件上传必须限制大小、类型、文件名和存储位置，防止路径穿越。
- 网络访问需防范 SSRF；禁止直接请求用户提供的任意 URL。
- CORS、受信任主机、代理头和 HTTPS 策略必须按部署环境显式配置。
- 序列化不得使用不可信 `pickle`；解析 YAML 时必须使用安全加载方式。
- 错误消息和日志不得泄露内部路径、凭据、个人数据或数据库细节。
- CI 应执行密钥扫描、依赖漏洞扫描和静态安全检查。

## 12. AI 驱动开发规则

### 12.1 修改前

AI 助手必须：

1. 阅读仓库级及目标目录下的规则文件。
2. 检查相关模块、入口、测试、配置和调用方，不根据单个文件臆测架构。
3. 查看工作区状态，识别并保留用户已有修改。
4. 明确需求的验收条件、影响模块、数据迁移和兼容性风险。
5. 优先复用现有模式；新增抽象或依赖时说明其必要性。

### 12.2 修改中

- 变更必须保持聚焦，不夹带无关重构、格式化或依赖升级。
- 不得删除、覆盖或回滚用户未授权的修改。
- 新增行为必须同步添加或更新测试；修复缺陷必须包含回归测试。
- 不得伪造不存在的 API、配置项、测试结果、迁移结果或命令输出。
- 不确定第三方 API 时，应查阅当前版本的官方文档或本地类型定义。
- 不得以 `Any`、空异常处理、禁用检查、跳过测试来规避问题。
- 生成数据库迁移、权限逻辑、并发代码和安全相关代码时必须进行额外审查。
- 大规模机械修改应拆分进行，并在每个阶段验证，避免一次性改写大量无关文件。

### 12.3 修改后

AI 助手必须按项目可用情况执行并报告：

```bash
uv run ruff format --check .
uv run ruff check .
uv run pyright
uv run pytest
```

涉及特定能力时，还应执行：

- 数据库变更：迁移升级、降级或前向修复验证。
- API 变更：OpenAPI/契约兼容性检查。
- 依赖变更：锁文件一致性与漏洞扫描。
- 并发或性能变更：针对性压力、竞态或基准测试。

最终说明必须包括：修改内容、关键设计决定、验证结果、未执行检查及其原因、已知风险。不得声称未实际运行的检查已经通过。

## 13. CI/CD 质量门禁

合并到主分支前，CI 至少必须通过：

1. 锁文件一致且可冻结安装。
2. `ruff format --check` 与 `ruff check`。
3. Pyright 严格类型检查。
4. 单元测试和集成测试。
5. 覆盖率阈值与新增代码覆盖率要求。
6. 依赖漏洞与密钥扫描。
7. 构建产物验证。
8. 涉及时执行迁移、契约和端到端测试。

发布产物应由 CI 构建一次并在各环境间晋级，禁止在生产环境重新构建。发布必须具备版本标识、变更记录、回滚或前向修复方案。

## 14. 完成定义（Definition of Done）

一项变更只有同时满足以下条件才视为完成：

- 验收条件已实现，失败和边界行为明确。
- 模块边界与依赖方向未被破坏。
- 类型、错误处理、日志和安全要求符合规范。
- 相应层级的测试已添加并通过。
- Ruff、Pyright 和相关 CI 检查通过。
- API、配置、迁移和运维文档已按需更新。
- 兼容性、部署、回滚和数据风险已评估。
- 无临时调试代码、硬编码密钥、无依据忽略项或未追踪的 TODO。

TODO 必须关联任务编号，并说明触发条件或清理期限；不得使用 TODO 代替当前变更所必需的正确实现。
